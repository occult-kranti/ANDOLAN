# Gameplay video study — VIDEO-GAMEPLAY-01

The supplied `gameplay.mp4` shows a third-person match ending in victory and several post-match pages. The strongest transferable findings are a compact persistent match HUD, clear action-block feedback, visible equipment/economy progress, and a deliberate transition from the live world into a readable result. These are interaction patterns for original YUGA work; no source-game art, characters, icons, map geometry or audio was imported.

This is a **sampled full-timeline visual review**, not a claim that every video frame or every sound was watched. The reviewer actually viewed all six 30-second timeline contact sheets, all seven targeted contact sheets and seven selected original-resolution frames. Audio was not reviewed. No opened shop menu or hero death/respawn screen was observed in these samples.

## Three highest-impact changes for native YUGA

These are bounded implementation recommendations for the existing offline product. The native comparison below is source inspection, not an executed native visual/input review. Runtime verification belongs to the integrating owner. Other workers' current edits may supersede the recorded source hashes.

1. **Turn live status into a compact match dashboard with one clear action-state message.** `confluence_world.gd::_build_ui` currently creates a sizeable top-left title/status/objective card, a top-right atlas, separate relay/traversal/help cards and the Rama HUD. `_update_practice_hud` already owns real core, wave, lane and gold values. `rama_hero_hud.gd` already distinguishes active, ended, returning and paused, and shows reload/draw/recovery/queue state. Retain those authorities while reducing repeated permanent copy, keeping core/wave/mode status compact, grouping resources/equipment and keeping health/abilities immediately readable. Keep native indigo/ivory/gold styling; do not blindly clone the source's small vertical health indicator. **Acceptance:** actual offline lane entry, attack, cooldown, reload/empty bow, respawn, pause and round end each show the correct existing state and current binding; slots never look ready while the runtime rejects input. At 960×540 and 100/150/200% UI scale, essential state and focused controls remain visible, and the center aim/hostile-warning area remains clear. Resize, return from a modal and reset twice without overlay/input leakage. A future stun/sleep UI requires an actual simulation status contract first.

2. **Complete a small, original earn–spend–feedback loop.** Baseline `lane_army.gd` exposes earned gold and a `gold_changed(total)` signal; the inspected live HUD reports gold but contains no spending control. The clip establishes visible equipment progression and a receipt after a purchase, while leaving its menu rules unobserved. Use an original YUGA store with a short explicit item list and existing native focus components. The build panel is implementing this separately; this study does not prescribe source-game items, prices or categories. **Acceptance:** after real lane earnings, open the store from a current binding; show balance, item effect and price; accept a valid purchase exactly once; reject insufficient funds without mutation; apply the purchased effect to the actual runtime; show a concise receipt and updated balance/equipment. Closing/cancel restores pointer capture and prior gameplay/modal focus. Round reset clears upgrades and spending exactly once, outcome prevents further purchases, and repeated opening cannot trigger attacks through the modal. Verify in a native input journey, not only a data test.

3. **Make the existing core outcome a complete, reviewable result flow.** `world_outcome_summary.gd` already displays the true winner and final cores inside the pause menu, while `_update_practice_hud` points players there. Evolve that real event into a restrained world outcome followed by an original Rama/local-practice summary with clear restart/return actions. Record a frozen end-of-round snapshot before restart; only show totals actually recorded. A cumulative chart is a later addition if real timestamped events exist. **Acceptance:** Sun win, Moon win and simultaneous-core draw each present the correct result once; troop/relay progression and purchases stop using their authority rules; result navigation neither resumes a terminal round nor changes the winner. Summary values equal the captured battle/runtime report. Keyboard and pointer can reach restart and return; cancel/back has a defined destination; restart creates a fresh generation with no previous result/equipment and no duplicate signals. Verify repeated end→results→restart and end→menu→re-enter journeys. No fabricated multiplayer rows, rank, MVP comparison or network status.

## Reproduction, checks and remaining limits

`ffprobe -v error -show_streams -show_format -of json <snapshot>` produced the retained intake metadata. Individual frames were decoded with `ffmpeg -nostdin -v error -ss <seconds> -i <snapshot> -frames:v 1 -threads 1 <fresh-output.png>`, at most four concurrent decoder jobs. Contact sheets were composed with Pillow under `/workspaces/tooling/yuga-native-python312/bin/python`; captions state requested source time, and retained PNG originals are unchanged. The first attempt to build contact sheets using default Python failed because Pillow was not installed there; no decode/source data was changed, and the known project Python succeeded.

Evidence verification checks indexed hashes, frame counts and 640×360 dimensions. There were no runtime changes in this task, so native gameplay tests were not run. A broad initial source search accidentally reached the evidence archive and was truncated; subsequent comparison read only the six explicit runtime paths recorded in the receipt. That truncated search was not used as acceptance evidence.

Remaining gaps: the footage does not establish a complete pre-match flow, readable store menu, death/respawn flow, accessibility settings, input mapping, audio cues, authoritative network behavior, source game's exact tuning or reproducible physical-GPU performance. All three proposed implementation changes still need native visual/input checks by the integration owner.
