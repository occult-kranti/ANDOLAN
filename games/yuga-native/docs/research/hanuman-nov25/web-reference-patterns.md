I fetched the six user-supplied pages on 25 November 2026 over HTTPS with normal TLS and bounded response sizes. I examined their delivered HTML, declared redirects and script links. A successful HTTP response establishes page delivery. To identify a renderer, startup sequence, camera controller or server from a deployed game requires further evidence such as an observable runtime or published source.

## A practical architecture from the sources that are accessible

**Keep the existing browser renderer and server boundary.** The inspected workspace uses PlayCanvas 2.23.3, Vite 8.3.4 and the Node `ws` package. The public YUGA page returned a 6,480,261-byte HTML shell with inline JavaScript and 21 distinct hashed GLB paths. I fetched the published browser Hanuman GLB and confirmed its 3,372,660 bytes match the existing local browser model. Its glTF 2 header and nine animation names parse correctly. The newer native Hanuman model and five-slot rules are a separate trial build. The deployment design already distinguishes static bot Practice from a separately hosted HTTPS/WSS authority. [Build config](../../../../../vite.yuga.config.ts) · [Published browser game](https://occult-kranti.github.io/ANDOLAN/yuga/) · [Deployment guide](../../../../yuga/docs/DEPLOYMENT.md)

**Make the first playable route smaller.** The current browser lobby waits for all 14 hero loads and all seven unit models before allowing a match, then warms the first view. Its deduplicated GLB promises and separate meshes/textures already provide a cache seam. Start a Hanuman trial with its selected hero, a light version of the original court and the five required targets. Keep decorative and gallery assets out of the critical path. Preserve cancel, retry and generation checks so a late download cannot open a discarded match. Before a rollout, compare cold and warm time to first controlled frame, actual transferred bytes, and interruption on a throttled connection. Keep two-player WSS qualification separate. [Browser startup](../../../../yuga/client/main.ts) · [GLB library](../../../../yuga/client/hero-models.ts)

**Keep physics and camera responsibilities clear.** The provided sites no longer expose the controls. YUGA already gates pointer lock behind user input, supports drag and touch alternatives, and sends neutral input on blur and page hide. The view clips the shoulder camera against world bounds and eases only its return; character physics stays with authority. The MIT Godot kinematic-character demo independently illustrates camera-relative steering, fixed physics steps, `move_and_slide` and a separate bounded follow camera. The native Hanuman trial already has a `CharacterBody3D` and `SpringArm3D`. Converge the user-facing behavior across the routes and exercise keyboard, pointer-lock loss, wall/camera contact and target occlusion through their existing tests. [Browser inputs](../../../../yuga/client/main.ts) · [Browser camera](../../../../yuga/client/world.ts) · [Godot movement source](https://github.com/godotengine/godot-demo-projects/blob/281a99f02178db944bcddef39aa694e3bfbe354a/3d/kinematic_character/player/cubio.gd) · [Godot camera source](https://github.com/godotengine/godot-demo-projects/blob/281a99f02178db944bcddef39aa694e3bfbe354a/3d/kinematic_character/player/follow_camera.gd) · [Demo license](https://github.com/godotengine/godot-demo-projects/blob/281a99f02178db944bcddef39aa694e3bfbe354a/LICENSE.md)

**Use the same source art with separate runtime budgets.** The exact PlayCanvas version in this project already parses glTF/GLB asynchronously, resolves external resource buffers and has an explicit Draco mesh-extension path. Try one measured browser-optimized export of the revised Hanuman, retaining the original source rig, action names and provenance. Compare plain and compressed cold-download time, decode, texture memory, animation import, hand/weapon contact and foot clearance before selecting a default. The MIT engine code is a reusable tool; art and audio retain their own license or original provenance. Recreate the native effect cues in the browser only from YUGA's owned ability data and event boundaries. [Pinned GLB parser](https://github.com/playcanvas/engine/blob/b7655d8fccc1284678af8f098b26b0725e20dd3a/src/framework/parsers/glb-parser.js) · [PlayCanvas license](https://github.com/playcanvas/engine/blob/b7655d8fccc1284678af8f098b26b0725e20dd3a/LICENSE) · [Native event and art design](../../HANUMAN_GAME_DESIGN.md)

All six links were checked. No third-party game was launched because the supplied pages did not provide a playable route. The public YUGA check covered HTTP delivery and the browser model bytes. It did not measure JavaScript execution, startup latency or an online session.

## Candidate packet for the browser loading and presentation panel

The first change is a small, separately identified Hanuman court in the existing browser client. Verify the published browser route and native trial as baselines first. Retain the rest of the gallery, existing Practice match and online protocol. This packet proposes browser work. The HTTPS response checks above do not count as a trial implementation.

| Review | Candidate change | Evidence required to close the review |
| --- | --- | --- |
| Loading and reentry | Read a required asset list through the existing scene-owned GLB library. Fetch Hanuman and the playable court first. Fetch optional gallery and decorative assets later. Use the current request token, abort state and first rendered frame gate.
