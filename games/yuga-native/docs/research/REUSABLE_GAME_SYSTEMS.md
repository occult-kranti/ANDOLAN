# Reusable systems for the native YUGA build

Reviewed 16 October 2026, America/New_York. Live public GitHub metadata and pinned source/license files were inspected for **eight project groups**, plus a bounded comparison of three REA forks and two sections of an author-hosted programming book. [Machine-readable provenance](reusable-game-sources.json) records revisions, exact paths, SHA-256 values, reading scope and recommendations. These were source inspections: this pass did not run these games/tools, analyze commercial client binaries, parse a commercial replay, download art packs, or establish visual parity.

## Three immediate choices

1. **Adapt small Godot TPS patterns into the existing native project.** Use the official demo's separate local input, authoritative movement/projectile simulation, aim/strafe animation states and release cues as design references. Keep YUGA's original hero assets and protocol-2 server contract. The current demo project declares **Godot 4.7**, although its README says current stable 4.x; its `project.godot` also retains a `Bullet` physics setting. It is not a tested drop-in Godot 4.6 project. Port only the needed behavior and validate it in the installed 4.6.3 runtime.
2. **Use the official Godot character/network demos for narrow edge cases.** The character example resets physics interpolation after teleport and bounds diagonal movement; the multiplayer example shows ENet peers, server-controlled spawn and disconnect cleanup. These are teaching examples, not a production matchmaking/authentication/anti-cheat stack. YUGA already has a server protocol: preserve it instead of adding a second authority just because an ENet sample is available.
3. **Evaluate native physics using the engine's existing integration.** Godot Jolt's README states that Jolt was integrated into Godot in 4.4 and the external extension is now in maintenance mode. For Godot 4.6, check the installed engine's built-in backend and exercise collision/stairs/fast projectiles before considering another extension. The extension explicitly does not guarantee deterministic simulation. Better physics, lighting and animation require actual measurements; installing another library does not prove them.

## Selected book reading

Robert Nystrom's [*Game Programming Patterns*](https://github.com/munificent/game-programming-patterns/tree/898b1f2e1818c80d7eed5eba98e9903ec13b7771) was fetched from the author-hosted repository at `898b1f2e`. This pass read the README/license and these selected chapter sections, not the whole book:

- **Game Loop, lines 373–493:** fixed simulation updates with flexible rendering; bounded catch-up to prevent a stalled loop; smoothing between updates and the risk of extrapolating through a later collision. For YUGA, rendering/interpolation must not grant damage, movement distance or extra casts. A delayed snapshot should not become permission to simulate a second authority.
- **State, lines 359–491:** state entry/exit behavior and separate concurrent locomotion/equipment states. For YUGA, centralize action cleanup on cancel/death/pause/disconnect and avoid a combinatorial “running-with-every-weapon-and-every-cast” state list. Interaction rules still need explicit priority.

The prose files use **CC BY-NC-ND 4.0**; other code files use MIT according to the repository license. These are original summary notes, with no book chapter or diagram copied into the product. No human-player result or game-quality guarantee follows from reading the book.

## Bounded implementation roadmap

These are proposed next gates, not completed implementation results from this research task. They retain the current protocol-2 integration work and assign independent ownership so art and systems can proceed together.

| Gate / owner | Concrete deliverable | Acceptance evidence |
| --- | --- | --- |
| N-S1 · movement/animation squad | Integrate native aim/strafe and action-layer policy with original Rama assets; weapon marker drives the visual release, accepted server event drives combat. Preserve existing movement authority. | Actual native recordings of idle→move→aim→fire→recover; no duplicate projectile or input after pause/death/reconnect; root-motion/clip changes do not silently alter server position. |
| N-S2 · network/economy squad | Extend protocol-2 event receipts and native result summaries with a source identifier, tick, actor, amount and reason; reject stale/duplicate input and impossible values at authority. | Two native clients against the current server; disconnect/rejoin and stale-sequence cases; wallet reconciliation from actual accepted receipts. Local bots do not satisfy online acceptance. |
| N-S3 · camera/physics squad | A small repeatable camera and movement course: tight corner, wall backing, stairs/seams, jump/landing, respawn, and fast shots crossing thin cover. Record engine/backend/version. | Native captures plus collision assertions; no wall penetration, teleport smear, diagonal speed increase or damage through cover. Compare actual timings before selecting a backend. |
| N-S4 · combat-content squad | Versioned original hero/content tables and an offline match-event report; preserve event-schema/version incompatibilities as explicit failures. | Roster/ability schema validation; reproducible bot matches with attributed damage/heal/gold/objective statistics; separately label human balance review as pending. |
| N-S5 · analysis squad | One supplied or otherwise accessible native/replay input, one bounded question, pinned REA/parser version, input hash and executable reconstruction/oracle comparison when possible. | Report supported findings, unknown call/data flow and counterexamples. No whole-game completion percentage inferred from one function. No commercial input was available in this source-read pass. |
| N-S6 · art/performance squad | Original materials, rigged models, action clips and effect boundaries reviewed in the real engine, with actual frame captures and before/after timing. | Compare neutral/lighted close views and gameplay distance; validate grip, skin deformation, feet, collision and effect timing. A concept image, renderer install or export-success message cannot pass this gate. |
