# Hero-edit stage mechanism and future reuse

The sealed crown-only schema6 implementation admitted one crown stage, three exact output GLBs, nine fixed generator/manifest/notice/import dependencies and an immutable schema5 parent. Its 72-check fixture and 91-source closure remain preserved. The lead subsequently accepted the sash UV correction and explicitly authorized the finite two-stage implementation below; the earlier source/check receipts are not relabeled.

The ordered schema6 successor keeps that same schema5 parent, embeds the unchanged crown stage followed by the fixed sash UV stage, and preserves the crown-only notice as an exact historical fixture. Stage 2 consumes the accepted crown intermediates and independently replays U×0.20/V×0.95 into only the three admitted UV record ranges. This avoids another historical wrapper for the UV edit. For future accepted edits, retain the flat sequence and version the format only when its validation contract changes, not whenever an output asset changes.

The finite stage table should contain immutable stage IDs and dependency pins, explicit input/output hashes for each affected LOD, the source generator and its own input dependencies, and a narrow edit-scope validator. A successor stage consumes the exact accepted prior output. Store those intermediate assets once in authoring history; the active runtime trio must match the final stage's outputs. No sealed generator, parent notice, old stage output or earlier test fixture is repinned in place.

Reuse the existing `_rama_source` path/symlink/hash checks, fixed dependency comparison, LOD mapping and before/after export checks. Factor the current `rama_crown_preservation` only when an approved new stage needs another scope. For example, a UV correction can allow declared TEXCOORD records of a named primitive while preserving positions, normals, tangents, weights, indices, other UVs and JSON byte-for-byte. A texture stage can bind its exact raw image, generator, import descriptor and selected material binding independently. Neither case warrants allowing all binary or JSON differences.

Geometry additions such as a shoulder or hair layer require a different explicit preservation rule: bounded new nodes/meshes/materials, stable existing rig/rest/skin weights and material payloads, a finite resource budget and proof of unchanged unrelated surfaces. They cannot be admitted through the rail-only P/N/T validator or a general “JSON may differ” switch. Their visual/contact reviews and imported payload comparison remain separate from the source proof.

Future edits must be composed in dependency order and revalidated as one final trio. Combining individually accepted outputs by last-writer copy would drop earlier changes. If two stages affect the same records, the second must declare and test its exact first-stage input, with an explicit conflict disposition. Keep schema6 output declarations fixed in reviewed code/data; never compute a trusted expected digest from the asset being validated.

Optional upper-hair compatibility remains an offline proof. Following source review, the lead rejected a growing runtime admission list because the helper checked guide metadata rather than hashing the active GLB. W2 restored the helper/guide to their exact original schema1 bytes and proved the nine hair accessors across old, crown and sash outputs separately. Package validation binds actual asset stages; the runtime guide hash continues to identify guide authorship. The superseded admission attempt remains historical evidence, not final implementation.

The current sash extension is the only implementation authorized by this note's later lead disposition. It retains all crown-only assertions and adds nine focused ordered-stage/UV checks; broader generic editing support remains a proposal. Another stage should be added only after an accepted source/art delta makes its required preservation rule concrete.
