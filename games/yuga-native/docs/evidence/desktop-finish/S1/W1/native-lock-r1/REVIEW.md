# S1 W1 — native first-draw lock evidence

The full textured mineral/frieze candidate did not render. The original attempt timed out at **130.628 seconds**; the unchanged-source debugger repeat timed out at **129.490 seconds**. Both produced zero images and stopped under the original 120-second no-progress watchdog. The production shader and gold candidates remain visually unaccepted.

The debugger repeat provides a concrete native blocking pattern. At process age60 seconds, a read-only GDB attach/detach completed in0.472 seconds. All five named WorkerThreads waited in `pthread_mutex_lock`, returning through native address`0x3dc09d2`. The main thread waited in `pthread_cond_wait`, through`0x480a6a5`, `0x3d3d597` and`0x3dc0b98`. Main and these five workers accumulated **zero CPU ticks across30.159 seconds** before the attach.

Exact binary string cross-references identify the worker lock as inlined `ShaderRD::version_get_shader` (`shader_rd.h`) and the main wait as `WorkerThreadPool::wait_for_group_task_completion`. The intermediate native function waits on the group, clears the version task slot and checks variant RIDs, matching `ShaderRD::_compile_version_end`. The `version_get_shader` disassembly takes the version mutex before entering that wait and has not reached its unlock. A narrowly scoped read of the same40-byte native mutex at`0x382703f0` gives owner TID220843, the main thread, using the x86_64 glibc owner field at offset8. All five workers' observed futex arguments point to that mutex. This ties the main-thread group wait to workers blocked on its held version lock; it is not a GPU-throughput measurement.

The release binary is stripped. Function identities above come from the **actual hashed binary's** literals and disassembly, supported by public4.6.3-tag source bodies. The fetched tag commit differs from the engine banner commit, so unverified source line numbers are not presented as symbols for this binary. The raw backtrace, executable mappings, native strings, disassembly and mutex observation are retained. The first run also has a5-second `strace -f -k` sample: it shows blocked unfinished futex calls but only unwinds active ancillary threads; it alone does not prove the engine call chain. Its late second `/proc` sample missed the normal teardown and is explicitly marked unavailable.

The supported settings review found shader/pipeline **disk-cache** controls, but no documented setting to disable asynchronous pipeline compilation. Disabling the disk cache does not remove the observed group-wait path. Existing cache hits return before a compile group is queued, so explicit Godot shader-cache seeding is a justified next tooling experiment. That would preserve shader quality and record cache provenance; a warm-cache success would not qualify a cold first launch or distribution. No such seeded run is included in this archive.

The successful gold baseline and the failed gold/textured attempts each log38 SceneForwardClustered cache misses ending with the same89c9… key. The last cache line is therefore not itself a failure discriminator or a proven material identity. The successful baseline retains101 Godot cache files; failed gold retains81 keys that form a subset, and the textured candidate adds one new custom key. Byte comparisons and exact seed candidates are retained without substituting a cache for source identity.
