Source contract: `shader_rd.h:179–209` keeps the Version recursive mutex through `_compile_version_end`. `shader_rd.cpp:555` submits ShaderCompilation group tasks at high priority, and line564 waits for completion. `_compile_variant` does not acquire the Version mutex itself. Thus high-priority pipeline jobs can occupy the pool on a mutex while the mutex-holder waits for queued shader group work. The fresh stack directly establishes function/wait identity, but contains no mutex arguments/owner read or queue snapshot; same-instance lock ownership and pending queue contents are inferred from source plus the separately retained older native capture, not newly measured here.

The proposed change affects only task priority in PipelineHashMapRD. Task IDs, compilation sets, output queue publication, explicit waits, Version locks, object destruction and shader readiness stay intact. On a pool of at least two workers, normal low-priority admission is capped below total worker count (`worker_thread_pool.cpp:818`); this prevents this class of pipeline tasks alone from occupying every worker at once and lets high-priority shader group tasks progress. The main thread's group wait blocks rather than stealing work; the low-priority pipeline workers blocked on a plain mutex do not enter cooperative waiting. Merely increasing the pool or low-priority ratio is not a principled repair while all involved pipeline jobs remain high priority.

Limits: this is not a proof of universal deadlock freedom. Cooperative waits can promote additional low-priority work; other high-priority clients can occupy workers; PipelineDeferredRD has a separate unchanged high-priority submission path; single-worker configurations require separate analysis. Changing priority may increase pipeline readiness latency under other load. Do not unlock the Version mutex around the wait without a separate publication/lifetime design. Do not remove shader features or alter caches to confound this cold comparison.
