# Mobile hero, animation and asset pipeline — M0

**Recommendation:** retain Rama's editable art, provenance and action-event contracts as the starting point, then build separately identified mobile meshes, animation libraries and binding profiles. The current desktop hero is not a mobile-ready asset. Begin with one complete Rama vertical slice at the intended elevated landscape match camera; multiply the roster only after that slice passes authored-art, combat-clarity and physical-device gates.

This is research and a production proposal, dated 2026-10-18. It makes no runtime, import, render, device-performance or mobile-release claim. “Mobile Legends quality” is an aspiration for readable original characters, coherent animation, polished feedback and reliable play; no parity benchmark was executed. No commercial client binaries were available, reverse engineered or extracted. Here, informal “4D/5D” means ordinary 3D assets with timed animation, effects and interaction, not a new rendering technology.

The [master roadmap](../MOBILE_PRODUCTION_ROADMAP.md) owns the proposed mobile **5v5** rules and M1–M18 schedule. Existing native Confluence is an offline Rama milestone; its broader desktop roadmap remains 6v6/fourteen heroes. Neither the fourteen briefs nor their invocation demonstrations are fourteen finished playable character packages. This document does not change those rules or claim that a camera conversion creates online authority.

## Authoring, retargeting and optimization sequence

1. **Intake and silhouette brief.** Choose an exact source/provenance baseline and one hero's gameplay role, weapon reach, height, camera footprint and major counter cues. Draw front/side/rear and elevated-camera silhouettes. Keep normal attacks, five current Rama actions and interrupted poses readable against both teams, terrain, night/day and overlapping effects. Fine embroidery cannot substitute for a distinguishable head/shoulder/weapon silhouette.
2. **Original source and mobile topology.** Preserve the editable high-resolution scene. Build a mobile retopology with deformation loops at shoulders, hips, wrists and knees; retain enough topology for drape folds and bow curvature at match size. Bake normals/AO and broad material variation. Consolidate materials deliberately; preserve alpha masks or replace them with a specified equivalent. Inspect linear normal/ORM data, sRGB base color, UV seams, tangents and mipmaps in the actual target renderer.
3. **Deform-rig contract.** Freeze units, facing, rest matrices, parent order, bind matrices, foot origin, socket names and mesh transforms. The existing Rama has two upper and two lower leg segments; a generic two-bone chain is not equivalent. Retain 164 bones in the first mesh/texture experiment. Trial a separate 64–80-deform-bone profile only after measuring bone/animation cost and proving retarget/socket/contact equivalence. Keep authored hand/string and weapon motion; strip control-only bones from the exported derivative, never blindly from the source rig.
4. **Retarget from the correct reference pose.** Use the actual inverse-bind/rest relationship and source global orientation, reconstruct target local transforms through the hierarchy, and explicitly preserve unmapped twist/attachment bones. Do not copy Euler rotations between differently oriented bones. The local [TPS study](../research/MOTION_RETARGET_IMPLEMENTATION.md) found a source default pose differing from inverse bind by about 1.46 radians and T-pose versus lowered-arm differences; its reference-transform correction is useful evidence, not a production animation approval. Test hips, shoulders, feet and weapon sockets before a full clip batch. Godot's automatic BoneMap warnings do not necessarily block an import [P3].
5. **Bake and edit motion.** Bake constraints/IK to the exported deform rig in a copy. Choose source sampling for observed angular/translation speed: a 30 Hz baked locomotion trial and 60 Hz fast-action trial are starting candidates, not universal requirements. Preserve clip endpoints, windup-hold pose, actual release/cancel transitions and loop continuity. Keep locomotion displacement in the movement owner; baked root travel is reference metadata or removed presentation travel, not a second actor translation. Author anticipation and recovery to the actual timing windows, not the reverse.
6. **Skin and mesh LOD.** Limit the mobile export to at most four nonzero influences per vertex, normalize weights, and verify finite indices and bind transforms. glTF can describe additional four-component sets; four is this proposed mobile policy, not a universal glTF limit [P2]. A two-influence distant profile is optional only if its deformed-surface error and visible motion pass. Preserve fingers/string at release, joint volume, garment clearance and silhouette when simplifying. Automatic Godot LOD explicitly warns about skinned-mesh defects [P3]; it does not establish lower skeleton/material/texture cost.
7. **Compress with an error oracle.** First remove constant channels and genuinely unused payload from the derivative; then reduce keys with quaternion hemisphere handling and measured interpolation error. Evaluate compressed and original clips at off-key times, transitions, holds and variable playback rates, including final skinned soles and sockets. Godot's animation optimizer is a documented import option [P3]. Download compression, key compression and runtime CPU/GPU savings are different measurements. Do not enable Draco/meshopt extensions, new quantization or platform compression until the exact engine/export/import path proves support and acceptable error. Keep an uncompressed reference.
8. **Import and package once per frozen candidate.** Run the pinned glTF validator, local structure/rig/weight/clip validators, then isolated Godot import and cold export under one owner. Inspect actual imported resources and every LOD, not only JSON metadata. Bind build, tool, import-setting, raw-asset and export hashes. Compare authoring preview with the packaged mobile build; offline Blender rendering cannot approve a shader, skin or clock in the shipped client.

Animation event tracks may label authoring landmarks, but they must not create damage, spawn authoritative projectiles or alter cooldowns. Keep gameplay timestamps and animation metadata separately versioned so compression, interpolation and LOD never reschedule a release.

## Timing, support and combat clarity

The current kit's combat clock owns commitment and release. Motion receives a request, approaches a windup/hold pose, and waits for the matching accepted release event. Cancellation removes the interrupted presentation without inventing a release; generation and cast IDs reject stale events. Preserve that contract in the mobile network adapter. A predicted windup can improve local response only under an explicit rejection/reconciliation policy; a locally finished animation cannot declare a hit.

Each authored action needs named anticipation, commitment/cancel policy, release, active area and recovery cues. Test early cancel, just-before-release cancel, released casts, retrigger, stun/death, reset, latency correction and out-of-order/duplicate events. Keep the visible muzzle, drawn arrow and actual projectile origin consistent. A cosmetic multi-arrow burst, oversized circle or long lingering glow must not imply extra projectiles, damage radius or duration. Reduced effects must retain dangerous boundaries, direction, team ownership and counter windows.

Support must use skinned soles and real ground, not only ankle targets or boolean locks. Observe the final modifier pose in the same callback/frame as the actor and floor sample. Preserve fixed world anchors while planted; release an unreachable target rather than move a planted anchor. Compare support-eligible and actually planted coverage, drift, penetration, gaps, release continuity and landing behavior. A smooth numerical curve that removes ordinary stance coverage is a rejection. Never lower the player/capsule, alter authoritative acceleration, hide contact defects in shadows or relax thresholds just to pass a candidate. Preserve the failed R4 evidence and test ordinary motion separately from adversarial reversals.

Desktop offline overview explicitly freezes the presentation alongside combat; inactive courtyard title idle intentionally continues. Mobile online backgrounding is different: the server match continues under the declared [network lifecycle policy](GAMEPLAY_NETWORK_AND_SERVICES.md). Stop stale local input, then restore a current authoritative snapshot/phase on resume. Do not replay missed damage or queued release effects as a burst, and do not let opening a local panel pause the room. Test death/respawn, teleport, LOD change and owner disposal during each state.

At the elevated camera, prioritize recognizable silhouette, facing, weapon sweep and ground-space warning. Use shape/value/motion as well as team color. Review hero identity and attack direction at the smallest intended on-device projected size, with effects disabled and in dense fights. Selection screens may use the close-view desktop-quality source under their own load/memory gate; loading all fourteen close-view heroes into a match is not implied.

## Provisional content and device envelopes

These are **planning hypotheses**, aligned with the [rendering packet](RENDERING_AND_MAP_PIPELINE.md), not achieved performance or measured Mobile Legends asset budgets. M1 selects named physical devices, renderer and resolution; M3 measures one complete hero, and M6/M12 extend the proof to ten players/ten distinct heroes.

| Hero-specific trial | Broad-access match | Main-target match | Admission evidence |
| --- | --- | --- | --- |
| Visible gameplay mesh | About 6–12k triangles | About 12–20k triangles | Actual submitted geometry across all visible heroes, shadows, units, world and VFX must fit the whole-scene envelope. A 4–8k distant LOD is an additional trial, not an accepted output. |
| Material surfaces | About 2–3 | About 3–4 | Opaque body, weapon and a restrained hair/cutout choice; count real submissions and overdraw. This requires a new material/binding contract beyond the existing 18-primitive layout. |
| Deform rig | Retain 164 for the initial geometry experiment | Same initial baseline | Separate 64–80-bone experiment only if measured benefit offsets deformation/socket cost. Do not assume a bone count predicts CPU time. |
| Texture inputs | Mostly 1k candidates | 1k–2k candidates | An initial 8–12 MiB resident texture allowance per in-match hero is a hypothesis; measure actual GPU format, mip chain, shared resources and import copies. It is not source PNG/GLB size. Ten such allocations consume 80–120 MiB before the rest of the scene. |
| Presentation update | Local hero at display rate; distant actors 15–30 Hz with interpolation | Near actors at display rate; distant roughly 30 Hz | Keep simulation and release timestamps unchanged. Evaluate visible cast/foot/socket motion and pose interpolation; never lower gameplay warning/event precision. |
| Aggregate animation work | Investigate a 1–2 ms CPU envelope for ten visible heroes | Same starting investigation | Profile sampling, skeleton, contacts, secondary, face and allocation separately. This is an experimental allocation within the scene budget, not a promised engine cost. |

The full scene targets sustained 30 FPS (33.3 ms/frame) on broad-access devices and tests a 60 FPS (16.7 ms/frame) tier on the main devices. CPU/GPU pipelines overlap; their timings cannot simply be added into an FPS claim. Use actual Android Adreno and Mali devices and a separately qualified iOS lane, not only an emulator or cloud software renderer. The current project `.mobile` override is Compatibility, whereas the proposed Mobile renderer needs its own qualification; a desktop Forward+ result cannot stand in for either.

An initial diagnostic should run at least twenty minutes after warmup with ten visible heroes, wave peaks, simultaneous abilities, camera motion, deaths/respawns, menu transitions and background/resume. Final qualification follows the stricter [device-validation contract](DEVICE_VALIDATION_AND_RELEASE.md): ten minutes of warmup, then at least thirty measured minutes or two full matches (whichever is longer), repeated for three runs. Record exact device/OS/driver, renderer, resolution, build/asset hashes, p50/p95/p99 CPU/GPU/frame times, stalls, allocations, process footprint, resident textures, thermal state and battery conditions. Separate screen-recording overhead. Repeat cold loading, shader first-use, low-power and memory-pressure cases. Scale secondary motion, face work, decorative VFX and resolution before hiding essential tells or changing combat. Artist and player review decide whether reduced quality still communicates the same action.

## Roster scaling and six-worker packets

Rama is the first vertical slice in M3. M11 adds heroes 2–5, M12 reaches ten distinct complete heroes, and M13 completes fourteen under the master schedule. Ten copies of Rama can stress rendering/network seats earlier; they are not ten characters or a unique-selection draft. Distinct body/weapon families need separate motion reviews: an archer, heavy brawler, staff/support hero and a tail-bearing Hanuman expose different constraints. Shared locomotion and rig templates save authoring effort only after each derivative passes silhouette, contact and ability checks.

Plan roughly 20–35 motion assets/states per hero as an initial inventory: idle/locomotion/turns, attacks, ability anticipation/hold/release/recovery, cancel, hit, death/respawn and selection presentation. The present Rama library has 23 clips; the estimate is not a requirement that every ability use a separate clip per phase. Fourteen heroes could imply 280–490 clip/state variants before directional sets, weapon variants and retakes. Re-estimate after M3 using actual artist/animator throughput and review failures; do not convert that arithmetic into a delivery date.

Use the master's stable W1–W6 identities. The following are **six coordinated work packets within each hero batch**, not a new parallel six-round roadmap:

| Owner | Concrete packet and outputs | Dependency / completion gate |
| --- | --- | --- |
| W1 — rules/authority | Freeze each action's commitment/cancel/release/active/recovery semantics, geometry and event IDs; define network correction/background behavior | Required before animation and telegraph timing is final. Replayed, stale and duplicate events cannot create extra releases. |
| W2 — touch/screens | Lock landscape match camera, aim/facing feedback, occlusion limits, selection-view size and accessibility/reduced-effects controls | Camera/screen-size contract feeds W3/W4. Real touch aim/cancel and safe areas remain readable while the hero animates. |
| W3 — hero/motion | Original character brief and provenance; editable source; mobile topology/rig/skin/library/LOD; socket/contact and transition reports; source-bound capture request | Owns this pipeline. Depends on W1/W2 contracts and W5 device envelope. One complete imported hero with honest failed-candidate evidence before roster multiplication. |
| W4 — world/units | Representative ground/slopes/obstacles, lane-unit silhouettes, ten-actor staging and backdrop/value/lighting cases | Ground and world scale must agree with movement authority. Provide real contact/crowding fixtures, not only a beauty turntable. |
| W5 — rendering/build/tools | Pin Blender/exporter/validator; implement isolated skin-aware optimization/import/package adapter; measure animation/material/texture costs on named devices | No static-only optimizer on heroes. Freeze exact sources/exports and serialize heavy import/render. Build the Android/iOS tool lanes with platform owners. |
| W6 — independent QA/security | Challenge licenses/ancestry, rig/clip/socket failures, LOD/lifecycle/event order, match-camera clarity and physical-device traces; retain raw originals | Independently accept or reject each bounded claim. Structural tests, artist review, actual play and device measurements remain separate gates. |

Dependency order: W1/W2 freeze gameplay/camera semantics; W3 and W4 create the actor/scene fixtures against W5's proposed profile; W3/W5 produce a frozen imported candidate; W6 reviews exact continuous captures and device results; the lead admits a bounded result or schedules correction. W6 can challenge source and legal assumptions early without waiting for a render. A shared heavy lane remains serialized; six workers do not imply six simultaneous engines.

## Character and device acceptance gates

| Gate | Required evidence | Reject or keep open when |
| --- | --- | --- |
| A0 — provenance | Exact source/asset/tool hashes, license texts, contributor rights, editable source and export recipe; original design/cultural review | Original project source is missing without disclosure, rights are inferred from engine code, or a reference likeness is copied without clearance. |
| A1 — structure | All LODs import; rig/rest/bind/weights/morphs/materials/sockets match their declared profile; retained desktop contract still passes | A reduced rig is admitted by disabling 164-bone checks, surface consolidation breaks masks, or compressed output lacks a valid reference comparison. |
| A2 — authored animation | Paired continuous starts/stops/turns/strafe/backpedal/aim, support acquisition/release, jump/land, each action/cancel/retrigger, pause/resume/reset/teleport, at 30/60/120 simulation schedules | Skinned penetration/gaps, sliding, popping, lost ordinary support, hand/string drift, collar intersections or event shifts remain outside the declared gate. Tests alone cannot approve motion. |
| A3 — elevated-camera art | Actual packaged on-device neutral/day/night/backdrop views and continuous ten-actor fight; independent hero/ability/direction/counter identification; artist signoff | Only close-up concept art or desktop stills exist; labels/color alone distinguish heroes; low tier hides warnings or misstates area/count/duration. |
| A4 — authority and lifecycle | Same cast IDs, accepted/released/cancelled chronology and gameplay geometry across quality/LOD; background/rejoin/death/owner-disposal evidence | Animation emits damage, stale events replay, clocks diverge, or the room pauses because a client opens UI. |
| A5 — device and package | Exact Android/iOS artifacts on named devices, sustained traces, memory/thermal/input/first-load and LOD-transition captures, including ten distinct heroes when roster is ready | Only cloud timing, average FPS, metadata counts, emulators or an export success are available. Missing iOS hardware/build-lane evidence keeps iOS open. |

Publish a character packet only with its exact accepted profile, limitations, remaining defects and independent reviewer. Preserve prior bytes and rejected candidates. A3/M3 is one accepted character; M6 is ten-player networking; M13 is roster coverage; none alone establishes a finished, balanced mobile MOBA.
