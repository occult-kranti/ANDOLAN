# YUGA mobile: touch combat and screen migration

M0 / worker04 · 18 October 2026 · design and implementation plan, **not implemented or device accepted**.

This plan adapts original YUGA to a landscape, elevated-camera **5v5** mobile game alongside desktop, with all playable heroes unlocked. Mobile Legends: Bang Bang is the requested quality reference for clarity, responsiveness and finish; its assets, exact interface and undocumented rules are not implementation inputs. This research did not run its binary, inspect its videos or establish comparative quality. The native repository currently implements offline third-person Rama practice. Its existing production documents describe 6v6; 5v5 below is the new proposed product contract and must be reconciled by the integration owner before queue, draft or authority code changes. The separate browser 3v3 authority is not a native 5v5 backend.

## 1. Combat layout: the playable field comes first

Use one safe interactive rectangle and three permanent information regions. At a 1280×720 design canvas, start with these dimensions, then calibrate against physical devices. They are proposed tuning values, not Android standards or measured comfort claims.

| Region | Initial composition and behavior |
| --- | --- |
| Upper left | A compact tactical map, approximately 176×176, with team bases/lanes and a separate 48-unit Expand target. An expanded map is a modal information view with explicit Close/Return to hero. Preserve map geometry proportions; fit its 140×260 world bounds inside the square rather than stretching roads. |
| Top center | Team score/objective state and match clock on one quiet strip. Network state appears only when useful. A new event briefly expands below this strip rather than shifting combat controls. |
| Upper right | Settings/menu, team communication and ping entry, separated from the aim cancel zone. Match settings opens a panel and continues online simulation; offline training can still pause. |
| Lower left | Movement activation zone: first eligible finger anchors a joystick in a bounded thumb region. Initial radius 66, dead zone 10, output magnitude clamped to one. Optional fixed-stick mode uses the same output curve and maximum speed. Keep edge/gesture gutters free. |
| Lower right | Large primary attack, initial diameter 92; four distinct ability controls around it, initial diameters 64–72, with at least 12 between hit boundaries. Keep Dawn Volley visually distinct by glyph and position, not just color. Reload sits above primary with a separate hit region and ammo readout. A preview-only Cancel target appears inward/upward, beyond the ordinary ability arc. |
| Near controlled hero / bottom center | Current health/shield and concise action notice. Critical state has an opaque-enough backing over bright or dark world scenes. Avoid a permanent five-description paragraph across the combat field. Labels expand in training and on intentional inspection. |

Do not add default sprint, jump, flight and grapple buttons just because those desktop actions exist. The first mobile MOBA slice is grounded Rama, primary plus four abilities, reload and communication. Traversal remains in the separate existing desktop/offline product until the game design and elevation authority explicitly admit it. If a later mode permits traversal, it gets a mode-specific control profile and its own counterexamples.

In the layout editor, show live hit regions and a protected gameplay window. Users can move/resize controls within safe bounds, mirror the movement/ability groups, adjust opacity, choose fixed/floating stick and reset only touch layout. Reject overlapping hit regions; present the conflicting controls instead of silently shrinking one. Offer a training test before saving. Layout changes during a match apply only after all fingers lift and the active command is invalidated; no relocation beneath a held finger.

Godot's `TouchScreenButton` supports multitouch but is a `Node2D` without Control anchors [G4]. For this directional cluster prefer one anchored `Control` layout plus an explicit touch router and drawn hit shapes. Keep standard `Button` nodes for menus. Avoid mixing per-button actions, global raw touches and emulated mouse clicks as three independent gameplay producers.

## 2. Pointer ownership and joystick contract

Each press is identified by **route epoch + gesture serial + event index**. The index alone is reusable after a lift; it is not a durable command identity. First hit-test the active modal, then touch gameplay hit regions, then free camera/selection regions. Capture ownership once, and retain it until release/cancel. A moving finger crossing a neighbor never presses it. A second finger inside an already-owned stick or ability cannot steal it. Ignore and log extra unowned fingers without clearing valid owners.

The touch router owns records like `{index, gesture_serial, owner, start_viewport_pos, current_viewport_pos, phase, layout_revision, input_epoch}`. Its output is semantic intent: `move_vector`, `aim_sample`, `primary_held`, `ability_commit`, `reload_edge`, `camera_pan`, `ping_intent`. UI controls do not call `kit.request_ability()` directly.

Movement uses `(current - anchor) / radius`, radial dead-zone remapping and `limit_length(1)`. Convert this vector through the fixed camera's horizontal right/forward axes, not the hero visual's animated rotation. Keep analog magnitude through locomotion; a diagonal cannot exceed unit speed. Touch aim and movement are independent. Zero movement immediately on owner release/cancellation; the physics controller still owns acceleration/collision. Record dead-zone, radius and response curve in bounded settings with finite numeric validation.

Use event `position` transformed into the actual UI viewport for hit-testing. Godot documents viewport coordinates and the multitouch `index`; `InputEventScreenTouch.canceled` must invalidate the gesture [G1]. For relative camera drag use `screen_relative`, because `relative` scales with content scale and changes apparent sensitivity across resolutions [G2]. Normalize pan sensitivity to the selected screen metric, then test the same physical drag at different render/UI scales. Do not mix raw screen deltas with virtual-canvas hit-test coordinates.

Menus may use touch-to-mouse emulation to activate standard Buttons [G4], but gameplay must admit only one event family. An emulated click from the same physical finger must never also fire the bow. Route-level capability flags and input producer identity are required; `set_input_as_handled()` alone is insufficient while the player polls global Input. Desktop mouse/keyboard and controller also enter the same semantic command seam after migration; detect active device for prompts, without changing combat rules.

## 3. Aim, targeting, preview and cancellation

Every ability has an explicit interaction profile: primary hold, directional, destination circle or movement direction. Default manual controls are precise; optional quick cast uses the same bounded target eligibility. Do not infer a placement from the viewport center while displaying a different preview.

State machine: `idle → captured → preview → committed → released → idle`, with `captured/preview → cancelled`. A release commits only for the same owner, route/input epoch and layout revision, with finite valid aim. An OS cancellation is never a successful release. After `committed`, the UI's cancel target cannot undo accepted windup, restore ammunition or refund cooldown. Existing simulation interruption rules own the cast from that point onward.

| Action and current rule data | Proposed touch profile and exact feedback |
| --- | --- |
| Kodanda: 40 m; 0.18 s windup + 0.22 s recovery; 0.40 s cooldown; native magazine 12. | Primary finger down acquires a valid aim and starts normal held-fire intent; drag adjusts direction for subsequent eligible shots. Each accepted shot snapshots direction and spends ammo once through runtime. Release stops future shots, not an already accepted arrow. Show ammo + reload progress; an unavailable target uses the configured manual direction or explicit no-target behavior, never an unseen enemy. |
| Piercing Dawn: 38 m; 0.65 + 0.30 s; 6 s cooldown; up to six hits. | Hold ability enters a directional line preview; drag thumb away from the ability center sets direction. Cover truncation is drawn distinctly from maximum range. Release submits one intent. Preview does not claim guaranteed hits or damage. |
| Measured Step: 4.5 m; 0.10 + 0.25 s; 5 s cooldown; movement duration 0.22 s; no invulnerability. | Tap uses current move vector, else current aim/facing. Drag overrides direction with a destination ghost. Preview uses the same wall sweep, bounds and minimum-distance rule as the accepted local kit. Show blocked endpoint explicitly. Do not move the character to the ghost in UI code. |
| Guardian Circle: within 16 m; radius 5 m; 0.55 + 0.30 s; 11 s cooldown; active 4.5 s. | Drag controls a ground reticle with range ring. Proposed short tap self-places if legal. Use invalid outline + short reason for cover/out-of-range/surface failure; invalid release cancels without a request. Authority can still reject a previously valid preview. Preserve exact submitted point in feedback. |
| Dawn Volley: 30 m; 0.95 + 0.55 s; 18 s cooldown; yaw offsets −0.105, 0, +0.105 rad; stagger 0.10 s. | Show three locked lanes before release. Release submits one direction; simulation then locks the lanes and schedules arrows. No repeated release events can create a second volley. Recovery/queued state is explicit. |

The values above are inspected offline kit values [L7], not proposed 5v5 balance approval. Current runtime ground-aim clamp of 15.5 m is narrower than the kit's 16 m Guardian limit. Resolve that discrepancy deliberately in the new aim adapter; do not copy two different radius calculations into preview and commit.

For directional controls start with a small stable neutral sector; tiny touch jitter retains the initial direction. A meaningful drag selects manual aim. For placement, map the radial thumb displacement to a bounded world offset around the hero, with a cursor above/inward from the finger, or offer direct-ground placement as a selectable profile. Both use one `AimResolver`; do not mix two sensitivity models mid-gesture. Freeze the preview's camera projection transform until release/cancel; suppress camera pan while an aim owner exists so a third finger cannot move the world under a placement. A terrain/collision generation change invalidates the preview.

Drag to the displayed Cancel region or beyond the configured cancel boundary to arm cancel. Use hysteresis so jitter cannot oscillate commit/cancel. Release while cancel is armed cancels. Returning inside restores preview before release. Cancellation feedback is a quiet retreat of the reticle; accepted commit gives immediate local acknowledgment followed by authority acknowledgment or rejection. Haptics are optional and short, with separate cues for commit and blocked intent; they never become required gameplay information.

Target selection for tap/hold primary uses a deterministic eligible set: alive, targetable, currently visible to the local team, within ability range and allowable line of sight. Select the chosen policy (nearest, lowest absolute HP or lowest HP fraction), then stable ID as final tie-break; expose the distinction in settings. Explicit hero portrait lock takes priority only while that target stays eligible. Provide a separate minion/structure priority option in training before competitive admission. Lose a hidden/dead/out-of-range target cleanly; do not silently jump to a different hero on the same held gesture. Keep manual skill direction available even when no target exists. Aim assistance is a game rule requiring desktop/mobile fairness review, not a private mobile damage bonus.

Online clients can preview against their admitted snapshot, but submit intent only. Authority validates movement limits, origin, range, cover, cooldown, ownership, visibility and target generation. Neither target portraits nor reticles can query or reveal hidden world records. A client prediction mismatch displays the accepted outcome and a short reason, without retrying the cast on a new target automatically.

## 4. Camera, minimap and pings

The proposed camera is elevated, fixed-yaw, landscape, with bounded pan and a persistent Return to hero action. Hero-follow smoothing must not move the aim sample after commit. The current overview camera is an offline inspection state which suspends play; do not reuse its pause semantics for a competitive camera.

The camera owner defines the projection, framing, maximum pan and occlusion treatment; input owns gestures. Free-field drag with no aim owner pans the camera, never the hero. A minimap-owned drag previews that location, with a visible camera rectangle; releasing restores follow unless the user explicitly chose unlocked camera. Retain a selectable locked camera profile. Pinch zoom is disabled during a competitive match unless shared visibility limits and device fairness are approved; training can provide camera examples without silently changing ranked visibility.

Use a shared combat visibility envelope across desktop/16:9/wide phones. Wider screens may gain margin for controls but must not admit extra hidden targets just because the world renderer shows farther left/right. Fog, culling and targeting are separate contracts; aim selection only sees admitted entities. The 140×260 world and its elevations remain original YUGA geometry. Project a ray against the intended gameplay surface; do not flatten elevated decks by choosing the first decorative mesh or always forcing army Y. Until shared elevation rules exist, restrict the mobile combat slice to the existing grounded plane and label raised-deck combat unsupported.

The minimap uses the existing manifest projection plus a tested inverse; map corners and Sun/Moon core positions must round-trip, and the hero heading uses the same anisotropic transform as roads. The current read-only map's complete offline unit feed becomes an explicitly filtered online map model with last-seen timestamps and no live hidden movement. Buttons/portraits need hit areas larger than their decorative marks.

Ping entry is a dedicated control, not an ambiguous primary-attack long press. Hold and drag to one of four labeled intents (Attack, Retreat, Gather, Danger), then choose a visible map point or allowed last-known point; release sends one event. Cancel uses the same preview rules. The server owns rate/burst limits, team routing and match sequence; the UI shows cooldown and mute state. A ping never implies a hidden target is present. Add text/icon markers and optional voiced cues with caption equivalents. Expose quick pings through keyboard/controller too. Free text/voice chat, moderation and accounts are separate dependencies; pings provide the first complete communication path.

## 5. Safe areas, scale, localization and access

The world may render edge to edge. Controls and text stay inside a converted safe rectangle plus a configurable comfort gutter. Godot documents Android/iOS support for `DisplayServer.get_display_safe_area()` and Android-only `get_display_cutouts()` [G3]. Intersect the display-safe rectangle with the actual window bounds and transform it through window/content-scale coordinates into the UI viewport; do not subtract device pixels directly from a 1280-unit canvas. Treat cutout rectangles as additional exclusions if needed. Recompute on window resize, orientation, split-screen/fold state and system-bar changes, and invalidate active gestures before relocating controls.

Android's official immersive sample explicitly says gesture navigation works even with navigation bars hidden [A1]. Do not promise that fullscreen removes system gestures. Keep movement/ability targets inward from edge-swipe zones; test both navigation modes, transient bar appearance, hole-punch/notch on either short edge and both landscape rotations. If an invalid/empty safe-area result is returned, use a conservative visible-window inset and a recoverable layout warning, not a zero-sized HUD.

Preserve `canvas_items` for sharp 2D UI while rendering changes its 3D scale independently; the Godot resolution guide states that `canvas_items` does not scale 3D [G5]. Test 16:9, 19.5:9, 20:9 and 4:3 landscape windows with safe-area exclusions. Keep the same input/world conversion at reduced 3D render resolution. Compact layouts collapse secondary notices/legends, never shrink hit regions beneath the configured physical target floor. Menus can scroll; combat controls cannot depend on scrolling to reach an ability.

Proposed mobile target floor is **48 Android dp equivalent** for ordinary actions, with larger combat targets and separation as above. This is a YUGA acceptance target, not a claim that 48 Godot units equal 48 dp: record density and window/UI transform in the device receipt. Start body text around 17–20 logical units and expose scale. Judge physical legibility on target phones. At 200% menu text scale, titles wrap, body grows and actions remain reachable via vertical scrolling with stable footer; match text scaling has a documented supported range and can expand noncombat panels without pushing essential abilities offscreen.

Translate whole messages using stable keys and placeholders; do not concatenate English control hints. Godot supports pseudolocalization and BiDi/mirroring, and warns that pseudolocalization alone does not prove CJK/RTL font support [G6]. Test English, Hindi/Devanagari, a long-text locale, Arabic RTL and CJK glyph coverage. These are coverage samples, not promises of launch translations. Mirror menu reading order; preserve world/team geometry and the user's chosen handedness. Do not automatically reverse camera/map directions in RTL. Format numbers consistently; keep player names isolated from surrounding directional text. Every added font needs a verified license and a fallback/shaping test before inclusion.

Cooldown, shield, target lock, team and cancellation need redundant shapes/text/patterns. Use darkened stable backplates rather than relying on world color to preserve contrast; target 4.5:1 for ordinary text, 3:1 for large text and essential nontext controls as internal design gates, then record measured pairs. Android's primary accessibility sample specifically highlights sunlight/contrast testing [A2]. Retain reduced motion/effects, separate camera shake and flash controls, scalable damage numbers, subtitle/caption settings and haptics off. Reduced effects must preserve attack boundaries, ally/enemy distinction, release timing and danger cues.

Menus require accessible action names, selected/disabled/loading state and logical focus. Follow Android's concise action-label guidance [A3]: label an icon “Settings”, not “Gear button double tap”. Verify the exported Godot build's actual platform accessibility exposure and TalkBack behavior before claiming screen-reader support; a custom rendered canvas is not automatically a native semantic tree. Do not announce every cooldown tick. Give critical status and route transitions bounded announcements, and provide keyboard/controller alternatives for layout editing, selection and aim-assist settings. Training must explain any control profile whose motor or visual assumptions exclude a player; offer configurable holds/toggles and clear presets without claiming complete motor accessibility from one joystick design.

A local input epoch is useful for UI invalidation but is not an authentication mechanism. Do not add a client-supplied cooldown, HP, hit list or damage amount.

## 8. Interruption and exploit counterexamples

| Trigger | Required state transition and invariant |
| --- | --- |
| OS cancels touch; notification shade; call; lost focus; app paused | Cancel every preview and release all touch-held movement/fire; increment input epoch; clear queued uncommitted commands. Offline simulation may suspend. Online sends zero movement best-effort and server expires stale movement; client cannot grant itself invulnerability or frozen cooldowns. Android's NDK sample demonstrates focus/window lifecycle callbacks [A4], but is not a complete production interruption solution. |
| Resume while the finger is still physically down | Require a fresh press after all stale ownership is removed. No auto-commit, auto-resume fire or remembered dash from pre-suspend. Reconnect snapshot admission is separate from the Android focus event. |
| Accepted cast during focus loss or menu opening | Preserve the authoritative decision and elapsed cooldown. Local offline pause retains its documented freeze behavior; online accepted casts continue by server rules. The Cancel visual only cancels unsubmitted preview. |
| Pointer index reused, duplicate releases, repeated input event or mouse emulation | A gesture can create at most one commit serial. A completed gesture is terminal; route/hero epoch mismatch rejects replay. Held primary can request later eligible shots only at the kit's rate, spending ammo exactly once for each accepted shot. |
| Death/respawn, practice reset, hero replacement, round end, scene unload | Invalidate owners, previews, target locks and action buffer together. Do not carry a target/queued cast across hero generation. Ended state blocks fresh combat; results wait for authority. |
| Two fingers press different abilities; press primary during accepted windup | Keep both pointer ownership records but allow only the kit-admitted action. Unaccepted secondary releases get a clear busy/queued response, with only the explicitly supported recovery buffer. Never cancel a committed cast to make the second one fit. |
| UI closes under a finger; safe area or layout changes | That finger's route epoch is obsolete; it cannot become a world action. Invalidate before layout reflow. Camera/movement are zeroed or retained only according to their explicit surviving owner, never inherited from the removed control. |
| Long background interval; stalled frame; device clock jumps | Local wall clock cannot complete simulation casts or award results. Use simulation time and monotonic interaction timing. Reconcile online state; do not burst-send accumulated input on return. |
| Target becomes hidden, changes team, dies or is recreated with same ID | Lock includes entity generation and visibility revision. Commit/authority revalidates; no hidden tracking or targeting leaked by portrait/cooldown feedback. |
| Malformed preference file / NaN aim / huge displacement | Existing bounded safe settings reader remains active; touch schema validates values before layout. Clamp finite normalized vectors, cap pointer records and reject invalid commands. Keep invalid original settings recoverable; do not execute configuration values. |
