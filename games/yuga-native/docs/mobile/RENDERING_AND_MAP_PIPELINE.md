# YUGA mobile rendering and map pipeline

Research proposal, 18 October 2026. Owner: mobile rendering/map workstream. This document proposes an original landscape, elevated-camera mobile edition alongside native desktop development. Mobile Legends is a public visual-quality reference for readable team fights, cohesive environments and polished animation; no client binaries, extracted content, proprietary implementation details or licensed game assets were supplied or inspected. This is not reverse engineering or a parity claim.

The recommended next step is a **Godot 4.6.3 mobile vertical slice using the Mobile renderer**, with a separately qualified Compatibility fallback and the desktop Forward+ path retained. Start with one original arena sector, Rama, a replicated hero and representative lane units. Measure sustained hardware performance before scaling to the proposed 5v5 mobile match. The existing product remains offline Confluence with one playable hero; the broader native roadmap still describes 6v6/fourteen heroes. A camera or renderer change does not decide that rules fork.

Evidence is pinned in [rendering-sources.json](rendering-sources.json). Links below identify source IDs from that ledger. The cloud machine is CPU/llvmpipe; it provides source inspection, import and structural checks, not phone FPS, battery, driver compatibility, thermal or visual-quality acceptance. No device benchmark, mobile export, heavy render or runtime change was performed for this report.

## 2. Renderer and device qualification

Official Godot 4.6 documentation distinguishes renderer from graphics driver [G-DOC-RENDERERS]. Mobile is a forward renderer on RenderingDevice (Vulkan/Metal and supported platform drivers); Forward+ is clustered forward and is optimized for desktop. Compatibility uses OpenGL/OpenGL ES and has a different feature/performance envelope. Driver fallback behavior is not an art-quality fallback strategy: detect the effective renderer and apply the matching material/lighting profile.

| Candidate tier | Initial renderer/profile | Intended use and qualification gate |
| --- | --- | --- |
| Broad-access Android | Compatibility, conservative shaders, ETC2, low internal resolution, 30 FPS cap | Qualify at least one older Adreno and one Mali device. Do not advertise support based only on OpenGL ES API availability. Device RAM, Android version, driver defects and sustained heat remain gates. |
| Main mobile target | Mobile, platform-native compressed textures, baked environment + bounded dynamic sun, 60 FPS candidate | Qualify modern Adreno and Mali separately; a chipset name or Vulkan feature bit is insufficient. Prefer sustained 30 FPS to unstable 60 when the device cannot maintain headroom. |
| Recent iPhone/iPad | Mobile using the supported iOS driver selected by the pinned templates | Physical iOS tests and Xcode export required. Qualify a supported older Apple device and a recent one; Android results do not qualify iOS shader correctness or memory pressure. |
| Desktop native | Existing Forward+ | Keep close-view hero/material review and desktop input workflow. Mobile profiles must not overwrite current desktop evidence or globally reduce the project. |

The renderer is a launch/profile decision. Do not switch entire renderers during a live match as a thermal response. Within a renderer adjust resolution scale, shadow distance/resolution, decorative VFX, secondary motion and target frame cap with hysteresis. Do not change camera visibility, collision, simulation rate, targetability or dangerous telegraph boundaries.

Mobile supports LightmapGI, reflection probes and glow; it lacks SSAO, SSR, SSIL, SDFGI, VoxelGI and volumetric fog in the inspected table. Use artist-authored AO/value separation, stable directional shading and baked environment lighting rather than requiring those features. Glow is optional polish; emissive lanterns and ability shapes must remain readable with it disabled. Compatibility also requires an actual material/color/AA review. MSAA exists in all three renderers; compare off/2× on hardware rather than assuming it is free [G-DOC-RENDERERS].

## 3. Provisional frame, content and memory envelopes

**Every number in this section is a starting hypothesis, not a measured budget or platform minimum.** Revise from traces on the target devices with OS/build/driver, renderer, resolution, quality preset, ambient conditions and capture interval recorded. Count frame submissions including shadows and transparency; node count and triangle count alone miss material cost and overdraw.

| Metric | Broad-access starting envelope | Main-target starting envelope | What to measure |
| --- | --- | --- | --- |
| Sustained frame cap | 30 FPS / 33.3 ms | 60 FPS / 16.7 ms, fallback 30 | Initial 20-minute diagnostics do not qualify release. For qualification use three runs per device/profile, ten-minute warmup, then at least 30 minutes or two full matches, whichever is longer, with a repeatable dense 10-hero encounter, lanes, menus and relaunch. Report frame-time p50/p95/p99 and stalls separately. |
| Main CPU / GPU investigation threshold | Each below ~24 ms | Each below ~12 ms | These overlap on pipelines; do not add them to predict frame time. Reserve margin for OS/network spikes; confirm available timestamps on device. |
| Internal 3D resolution | ~960×540 to 1280×720 | ~1280×720 to 1600×900 | UI remains native/safe-area aware; compare edges/telegraphs on actual screens. Wide aspect uses aspect-correct resolution, not stretched 16:9. |
| Visible submitted triangles, all passes | ~150–300k | ~350–650k | Include shadow cascades and VFX; vary geometry independently of pixel resolution to identify bottleneck. |
| Draw submissions, all passes | ~150–250 | ~250–450 | Record per-pass/tool counters; compare with material surfaces and duplicated health bars. These are investigation triggers, not engine limits. |
| Hero gameplay mesh | ~6–12k triangles, ~2–3 material surfaces | ~12–20k triangles, ~3–4 surfaces | Local hero/replicas/selection portrait have separate LODs. Ten visible heroes must fit the total scene envelope. Current assets are not claimed to meet these targets. |
| Lane infantry | ~0.5–1.5k triangles, ~1–2 surfaces | ~1–3k triangles, ~1–3 surfaces | Cap visible decorative detail, not authoritative units. Measure actual wave peaks; no current army cap is asserted here. |
| Dynamic lights affecting visible fight | One sun + ambient; ~0–2 local shadowless | One sun + ambient; ~2–4 local shadowless | Fill can be folded into ambient if acceptable; no per-ability dynamic light baseline. Gate aggregate overlaps from all scene owners. |
| Dynamic shadows | ~1024 atlas, ~20–30 m, 1–2 splits candidate | ~2048 atlas, ~30–45 m, 2 splits candidate | Actual camera coverage/bias/skin contact review; avoid baking and dynamic shadows double-darkening. No shadowed point lights initially. |
| Resident GPU texture working set | ~128–192 MiB | ~256–384 MiB | Unified memory is shared with OS/CPU. Track total process PSS/physical footprint too; these are not app RAM limits. |
| Total process working set | ~0.6–0.9 GiB candidate ceiling | ~0.9–1.3 GiB candidate ceiling | Include decoded resource copies, scene construction peak, shader caches and network buffers; reduce until OS pressure/relaunch tests pass. |
| Animation presentation | Local hero at display rate; distant replicas ~15–30 Hz with interpolation | Near actors display rate; distant ~30 Hz | Authoritative tick/release remains unchanged. Separate skeleton/contact/secondary/face timings. |
| Decorative transparency | Small localized meshes, no fullscreen layers | Similar, with optional small glow | Pixel coverage and overlapping layers matter more than emitter count; retain gameplay telegraphs in every profile. |

Memory arithmetic must be explicit. A 2048² RGBA8 texture is 16 MiB before mipmaps and approximately 21.3 MiB with a complete mip chain; a 1 KiB download does not imply a 1 KiB resident image. Block compression savings depend on format, alpha and mip levels. Inspect exported platform resources and driver residency rather than multiplying source PNG sizes [G-DOC-IMAGES].

Thermal acceptance includes cold and warm runs, charging versus battery, background/resume, OS low-power modes and an adverse ambient condition chosen by QA. Record battery energy/drain with the platform profiler where available and thermal state where exposed. Do not infer battery life from cloud CPU time. Use manual quality control plus conservative automatic degradation, clear recovery hysteresis and an option to select a stable frame cap. Thermal adaptation must not suppress enemy warnings or reveal hidden actors.

## 4. Original asset production path

### Authoring and import

1. Keep an editable `.blend`, texture source and source/license manifest for every kit. The existing reconstruction of Rama is editable but lacks original modeling history; use its documented equivalence gates before changing skin/rig. Blender is an offline authoring tool, not a runtime dependency [A-BLENDER].
2. Author at Y-up game scale through a tested Blender/glTF export conversion, apply intended transforms, use deterministic object/material/animation names and retain hero foot origin/socket conventions. Export plain `.glb` first; inspect imported bounds, winding, tangent basis, normals, skin joints, material surfaces and five combat actions [A-GLTF-IO, A-GLTF-SPEC, G-DOC-FORMATS].
3. Produce gameplay LODs from silhouette importance and projected size, preserving face/hand/bow/cast outlines. Keep 164-bone compatibility initially; generate simpler meshes without discarding vertex-color masks or bind order. Reuse one live rig. Current LOD selector thresholds are 420/160 projected pixels, with 15% hysteresis and a 0.15 s hold; the elevated view will often choose far sooner than desktop framing. Recalibrate against gameplay silhouettes and the coordinate space used for projected pixels, including dynamic-resolution behavior. Cross-fade only if the extra rendering/alpha cost is measured; discrete hysteretic transitions may suit the elevated view better [G-DOC-LOD].
4. Use meshoptimizer offline for triangle/index locality and controlled simplification, with seam/boundary/skinning constraints. glTF-Transform is a repeatable inspection/transformation candidate. Neither tool guarantees the resulting file matches YUGA's material-name/skin contract [A-MESHOPT, A-GLTF-TRANSFORM].
5. Do not enable Draco, `EXT_meshopt_compression`, KTX2 or required glTF extensions merely because a CLI exports them. First pass a minimal specimen through pinned Godot 4.6.3 editor import, export, clean-cache device launch and round-trip visual/animation comparison. Plain GLB plus Godot import compression is the baseline. A downloadable compressed container and a GPU resident compressed texture are different concerns.

### Texture/material choices

Use a small number of shared opaque PBR materials for city masonry, wood, vegetation and hero body/cloth. Palette/value design and baked broad detail carry the elevated view; close-up face pores and repeated thin gold edges should not dominate mobile fragment work. Use mipmaps for 3D textures, texture padding for atlases, appropriate normal-map import and linear channels for roughness/metal/AO. Check packed ORM channel conventions against actual Godot import; do not assume an external tool's packing is automatically wired.

Start with ~512–1024 textures for shared small prop/trim sets and ~1024–2048 for important hero/landmark atlases, then inspect projected texel density and compression. These sizes are provisional. Separate UI/text atlas import from 3D mip/compression presets. Avoid arbitrary 4K maps, unique material clones per prop, full-res face textures on tiny remote heroes and transparent hair sheets covering most of the head.

Godot's inspected image documentation specifies ETC2 as the default mobile VRAM compression path and ASTC for high-quality mobile compression; high-quality mode is for Forward+/Mobile. Use ETC2 for the qualified Compatibility profile and compare ASTC quality/size on the main tier [G-DOC-IMAGES]. Basis Universal is a Godot import compression option with small disk files and transcode cost at load time; it does not guarantee less resident VRAM than native compression. Benchmark normal-map/alpha quality and load latency before broad use [A-BASIS].

KTX-Software is useful for offline texture validation/encoding, not a reason to add a runtime loader. The Godot image page documents `.ktx` with 2D restrictions; it is not a blanket promise that arbitrary `.ktx2` glTF payloads work. The KTX repository is generally Apache-2.0 with bundled third-party licenses and a documented non-open Ericsson ETC-decoder special case. Before redistribution, audit the exact build and disable `LIBKTX_FEATURE_ETC_UNPACK` where appropriate; retain an SBOM/NOTICE. This report adopts no KTX binary or code [A-KTX].

### Lighting and VFX

Author separate mobile lighting profiles. Bake static environment illumination/AO with stable UV2 and retain sparse dynamic character shadows plus lightmap probes for moving actors [G-DOC-LIGHTMAP]. Godot baking uses the GPU; do not schedule a production bake on llvmpipe or call an unrun bake validated. Because the city is currently built dynamically from a manifest, create an editor bake assembly with the exact same immutable placements/chunk IDs, bake there, and package those scenes/data. Runtime-generated duplicate meshes are not automatically lightmapped.

Choose one of these scoped day/night strategies after a memory/composition test: fixed match lighting; baked indirect with dynamic key color/intensity; or separately packaged day/night variants loaded between matches. A changing sun cannot drag a baked shadow across the map; switching static direct-light bakes every frame is not the current `set_phase()` behavior. Preserve minimum enemy/route readability and identical visibility rules at both moods.

Keep water opaque with derivative-filtered broad normals; simplified mobile paving/masks should also feed the dry swamp border so there is no square seam. Prefer opaque or alpha-scissor foliage with trimmed geometry; evaluate aliasing on device. Avoid screen-color/depth refraction, fullscreen haze sheets and layered transparent moss. A cheap-looking ground can be improved with large authored value groups, edges and props before expensive postprocessing.

Reuse Rama's existing event-driven effect lifecycle. Pool immutable geometry/material variants, update dynamic ribbons only when needed, add screen-size/detail tiers and aggregate per-frame allocation counters. Prioritize cast boundary/impact/direction above ornamental quills or afterglow. Damage radius, windup timing and direction must remain truthful under reduced effects, shader fallback and thermal pressure. A per-hero twelve-cast cap cannot guarantee a ten-player fight fits the frame. Do not simply multiply the existing cap by ten.

## 5. Map designed through the mobile camera

The shared proposal with [TOUCH_UX_AND_SCREENS.md](TOUCH_UX_AND_SCREENS.md) is fixed-yaw elevated landscape with bounded pan and return-to-hero. Hero movement is independent of camera pan. Aim preview freezes the view transform until release/cancel; the UI/aim owner specifies this input contract. No pitch/zoom/camera offset values here are accepted gameplay measurements.

Begin with a sector containing a lane bend, river/swamp crossing, temple wall, lantern courtyard and one objective. Choose the framing from visible combat ranges and thumb-safe space, not a screenshot imitation. Test 16:9, 19.5:9 and tablet framing with actual safe insets. Minimap occupies upper-left; movement lower-left; ability/primary actions lower-right; settings/pings upper-right. Keep the active fight legible through the unobscured center. Wider screens must follow the shared visibility/targetability envelope; resolution or aspect changes must not reveal hidden enemies.

Map-specific rules:

- **Separate playable geometry from skyline.** City facades can supply a convincing original Indian-inspired urban silhouette, while short foreground walls, cutaway roofs and deliberate gaps preserve hero readability. A 12 m temple tower placed between camera and a 2 m hero needs an authored cutaway/visibility response, not a targetable enemy outline through secret walls.
- **Keep route purpose distinct from decoration.** Three lanes, rotations, jungle entries, return paths and objective approaches need different broad shapes/value groups. Decorative inlay/lantern pools must not look like damage telegraphs or capture progress.
- **Preserve collision truth.** Art replacements may improve walls and stair forms only within agreed footprints. Existing native traversal decks remain native-only until the authority/elevation work lands. Ground ray/aim uses the intended gameplay surface; water shading never manufactures a walkable height or hidden pit.
- **Screen-space density governs detail.** Dense roof filigree, reeds, tassels and reliefs belong in landmark close-up/selection views or texture bakes if they collapse to noisy pixels at gameplay zoom. Read silhouettes and team identity at moving handheld scale.
- **Chunk by local camera footprint.** Try ~16–32 m art sectors as a hypothesis, with neighboring sectors resident ahead of pan. Group repeated lantern/reed/stone instances into sector-local MultiMeshes; individual MultiMesh instances are not independently culled. Avoid one world-wide MultiMesh and one monolithic city mesh [G-DOC-MULTIMESH].
- **Do not assume occlusion fixes everything.** An elevated outdoor view exposes many roofs and ground pixels. Frustum/visibility-range/chunk culling comes first; measure occlusion overhead and usefulness on the actual camera before deploying occluder meshes [G-DOC-OCCLUSION, G-DOC-VISIBILITY]. Never let hidden presentation unload authoritative collision/rules.

## 6. Loading, streaming and packaging contract

Coordinate with [GAMEPLAY_NETWORK_AND_SERVICES.md](GAMEPLAY_NETWORK_AND_SERVICES.md). The required combat/nav/collision/content bundle is manifest-pinned and verified before match entry. Optional cosmetic chunks cannot block authority readiness or change targetability. Missing or corrupt required data blocks join/recovery; never substitute a decorative fallback for collision/rules.

Stage boot as authentication/allocation, manifest validation, local required-resource loading, bounded scene construction, warmup and server-ready acknowledgement. Show actual progress per stage from bytes/items/ResourceLoader status. `load_threaded_get()` can block if called early, while `.instantiate()`, mesh generation and GPU upload may remain main-thread costs [G-DOC-LOADING]. Budget work over frames; measure peak residency while old/new scenes overlap. Cancellation must invalidate late completions and prevent a disposed loading screen entering a match.

Godot Android export requires matching templates, documented JDK/SDK configuration and release signing/package validation; the inspected 4.6 page recommends JDK 17 and lists Android platform/build tools/NDK packages [G-DOC-ANDROID]. These are source instructions, not installed capability claims. Check store target-SDK and architecture policies at release time. Never save signing credentials in source or this research ledger.

iOS export requires macOS with Xcode and matching templates, team/bundle configuration and physical-device validation [G-DOC-IOS]. This Linux cloud checkout cannot establish iOS readiness. A zip inspection, simulator, Android screenshot or llvmpipe render cannot replace physical Apple device test results.
