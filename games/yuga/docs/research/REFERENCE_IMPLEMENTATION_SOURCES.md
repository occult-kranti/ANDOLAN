# Sources for an original playable mechanics lab

Audit date: 16 October 2026 UTC. This pass re-read bounded sections of five already-downloaded, pinned projects and ran one new REA analysis. It adds research evidence only. The first accepted implementation target is a small, independently authored hybrid-control lab retaining ordinary towers, waves and camps, followed by tested adaptations to YUGA. A separate pure control arena remains a possible later experiment. This document does not certify the lab as implemented or playable.

**Available:** open-source controller code, a small multiplayer tank game, a community Godot lane prototype, a Workshop compiler/custom-mode example, and community analytics code. **Unavailable in this task:** Deadlock or Overwatch commercial game source, supplied game binaries/replays, original assets, recorded reference matches, or an executable reproduction of either shipped game. A parser or Workshop compiler is not the underlying commercial simulation. Earlier, broader studies remain in [Deadlock engineering](DEADLOCK_ENGINEERING.md), [Overwatch engineering](OVERWATCH_ENGINEERING.md) and [Dota engineering](DOTA2_ENGINEERING.md).

## Concrete patterns and rejected shortcuts

**Movement — one input decision, one authoritative transition.** R1's [`Character.triggerAction`](https://github.com/swift502/Sketchbook/blob/62f4b7986fd1ce1e4f91daba89ef032c20a6ce55/src/ts/characters/Character.ts#L358) exposes `justPressed` only during a changed action's dispatch. [`JumpRunning.update`](https://github.com/swift502/Sketchbook/blob/62f4b7986fd1ce1e4f91daba89ef032c20a6ce55/src/ts/characters/character_states/JumpRunning.ts#L22) uses elapsed state time and `alreadyJumped` to request one impulse. These are useful separations between input, phase and actuation. However, `Walk.onInputChange` and `Sprint.onInputChange` contain sequential transition branches; `Character.setState` immediately dispatches input to the new state. That source structure can overwrite earlier transition choices, so the lab should specify one priority decision per simulation step. The source also uses clip completion to choose a falling state; the lab must keep collision, cooldown and damage timing independent of art duration. Its original jump delays are not measured Deadlock/Overwatch timings.

**Weapons — validate intent; emit acceptance, release and result separately.** R2's [`BattleRoom`](https://github.com/endel/tank-battle-multiplayer/blob/6339493130b4b1d4d28f0f52d17b2fba738c7d47/server/src/rooms/BattleRoom.ts#L134) receives move/target/shoot intent, creates projectiles on the server, applies shields/damage there and increments score at a lethal hit. The sample normalizes direction, but its `typeof` checks alone do not reject nonfinite inputs. Movement/projectile speed is expressed per update while reload/respawn use `Date.now()`, and tank hits are checked before block hits using discrete positions. These are source observations, not a network exploit or collision reproduction. The lab should use its existing bounded fixed-step clock, finite/clamped input, swept nearest-hit collision against actors and cover, explicit shot IDs and a once-only outcome. A muzzle flash is not evidence of accepted damage.

**Objective control — publish eligibility and contested state.** R3's [`ponto_controle.gd`](https://github.com/Mvfm-25/Deadlock-Manager/blob/c9252f69aac9088fee7151c883d7a4f91d98f51c/deadlock-manager/scripts/ponto_controle.gd) counts occupants by team, resets progress when empty/contested/ownership changes, and disables processing before emitting completion. This is an actual inspectable control-point rule, but not Deadlock's commercial objective design and not automatically the right rule for our arena. Choose and display the lab's own reset/hold policy. Recompute living eligible occupants from authority; do not depend on a client visual overlap or an unverified death-exit callback. R5's [custom mode](https://github.com/Zezombye/overpy/blob/5a7d0e294b8cad73b9701987bb584d0551d7fa4d/examples/skirmish_elim.opy) separately models waiting/setup/live and join-during-round behavior. Transfer the explicit lifecycle, not its teleport/hero-removal rules.

**Lane economy — preserve source identity and count each reward once.** R3's [`onda.gd`](https://github.com/Mvfm-25/Deadlock-Manager/blob/c9252f69aac9088fee7151c883d7a4f91d98f51c/deadlock-manager/scripts/onda.gd) advances a formation anchor, pauses when members have targets, and schedules replacement only when the last member dies. Its growing respawn delay is an author's simplification, not commercial parity. R4's [economy categories](https://github.com/deadlock-api/deadlock-api/blob/917e8537cb256cffd1417a56737adfed47370dd1/website/src/components/features/games/economy-definitions.ts) distinguish direct income from orb income and subtract assists where already included. This motivates an original ledger keyed by source entity/event and recipient, with explicit confirmed, shared, claimable, expired and spent categories. It does not establish present Deadlock split percentages or last-hit rules. Preserve missing observations instead of treating an absent analytics field as evidence of zero earnings.

This checks the selected guard under those mock conditions, not physics, landing, complete input dispatch, networking, animation feel or the games. The source reading and probe establish the narrow behavior; the graph supplies scoped provenance and explicit uncertainty. Prior economy probes are not counted as new tests.

## Lab acceptance before adaptation

These are proposed original acceptance gates, not results of this research pass. Use the existing TypeScript/PlayCanvas stack and native input harness; no new engine, backend or parser package is justified.

| Gate | Playable experiment | Required evidence |
| --- | --- | --- |
| L1 Movement | Run, change direction, jump/dash where supported, release, cancel a menu and respawn. | Held key does not repeat an edge action; simultaneous inputs follow documented priority; equivalent accepted input schedules produce equivalent fixed-step motion at low/high render rates. Hidden/stale input stops safely. |
| L2 Weapon/counter | Fire a finite-ammo weapon or cooldown attack at targets on both sides of cover; reload/cancel if that mechanic exists. | Exactly one accepted shot/release/result chain; closest valid collision wins; no fire while dead/paused or before cooldown. Counters use visible authoritative cues, with no invented reference constants. |
| L3 Hybrid control | Enter, contest, leave, die and finish a control-point round with ordinary towers, waves and camps retained. | HUD explains our hold/reset policy and competing finish conditions; dead/disconnected actors cannot capture; outcome freezes and is emitted once; restart clears phase and held input. Native traversal must match the visible zone. |
| L4 Lane economy | Clear one wave, secure or lose a contested pickup, purchase an upgrade and finish a short objective run. | Initial funds + per-recipient awards + claims − purchases reconcile with final wallets; expired/claimed rewards cannot pay twice; objective victory is independent of wallet size. |
| L5 Transfer | Select one demonstrated improvement and adapt it to YUGA after review. | Record source lesson, original rule, lab case and before/after YUGA evidence. Re-run affected simulation/native gates; preserve existing hero art, modes and public build unless explicitly changed. |

A lab can demonstrate a mechanic and reveal interaction costs without recreating complete rosters, commercial map layouts, progression, matchmaking, proprietary netcode or balance. Numerical tuning, player comprehension and enjoyment require subsequent measured play; source access alone does not establish them.
